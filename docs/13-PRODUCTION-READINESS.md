## Security review (Phase 5)
Method: automated checks above, then a read-through of the Phase 5 changes against `07-SECURITY.md` and `AGENTS.md` (authorization on every server path, tenant scoping, input validation, audit, idempotency). Done by the implementing engineer, so it is a self-review: it is not independent.

| # | Finding | Status |
| --- | --- | --- |
| 1 | An invitation sent before a workspace was suspended could still be accepted. | **Fixed** (invitations to a suspended workspace look like any dead link) and tested. |
| 2 | Jobs of a suspended workspace (meeting reminders, indexing) would keep running. | **Fixed**: they wait and run after restore; they do not count as backlog. Tested. |
| 3 | No Content-Security-Policy or HSTS. | **Partly fixed**: `frame-ancestors`, `base-uri`, `form-action`, `object-src` and (production) HSTS added; Turnstile still works. |
| 4 | No `script-src` policy (needs per-request nonces). | **Open.** Design before launch. |
| 5 | Operator accounts have no MFA; one stolen operator session can suspend any workspace or change any plan (no member content is reachable). | **Fixed in code (2026-11-03, ADR-025)**: operators need two-step sign-in. The operator on the pilot server must turn it on. |
| 6 | Authentication rate limits are per process and in memory (Better Auth default). | **Fixed** (ADR-019): counters are kept in the database (`rate_limits`), so every instance shares them; tested with two separate Better Auth instances. Still on only in production. |
| 7 | Entitlement checks cost one extra query per guarded call. | Accepted; no caching, so a plan change takes effect immediately. |
| 8 | Public forms and booking pages still rely on Turnstile (optional) plus volume caps. | **Mostly fixed (2026-11-02)**: Turnstile keys are set on the VPS and the secret is accepted by Cloudflare; the widget on a live public page was not seen yet because no form or booking page is published. |

Not done: an independent penetration test, a threat model for the operator surface beyond the notes in `07-SECURITY.md`, secret scanning and the dependency audit as CI steps (added to the workflow, not yet run there), RLS (OD-02).

## Launch blockers (must be resolved before real customers)
1. **Email provider.** The application refuses to start in production with the log transport. An SMTP transport now exists (`EMAIL_TRANSPORT=smtp` and `SMTP_URL`, ADR-019), so any provider that offers SMTP works. *Progress (2026-11-02):* the pilot uses the Plesk mail server on the VPS (mailbox `no-reply@fts-tech.co.id`; SPF lists the VPS, DKIM and DMARC records exist, DMARC is `p=none`), the SMTP login works with the app's credentials, and a real sign-up verification email arrived. **Still open:** password-reset and invitation emails were not sent end to end; delivery to other mailbox providers (Gmail, Outlook, others) and spam placement were not measured; the sending address is a shared VPS IP, so its reputation is shared with the other sites on it, and port 25 egress and PTR records were not checked; there is no bounce handling (ADR-019). Whether this server stays the sender or a transactional provider replaces it is a decision for the owner before real customers.
2. **Hosting and region (OD-01),** file storage (OD-04: the local-disk adapter is not a production store) and the database service with real backups. *Progress (2026-11-02):* the app, worker and gateway run on the owner's shared Plesk VPS and are public at `https://workspace.fts-tech.co.id` (Cloudflare in front, origin certificate, nginx proxy for the app and the WebSocket gateway, deploys through Plesk Git and a root-owned script, ADR-022; realtime checked in a browser). The region, the sizing for real load and a second host are not decided, the VPS is shared with other sites, and files are on that server's disk.
3. **Backups on the real stack:** a restore from an actual hot backup into a clean environment, measured recovery time and data-loss window written down, retention set (`12-OPERATIONS.md`). *Progress:* a daily `pg_dump` and files archive with 14-day retention exist on the VPS and a restore into a scratch database passed, but with an almost empty database, no file restore, and **no copy outside the server**. *Progress (2026-11-03):* `deploy/backup-offsite.sh` with a systemd service and timer (`fts-backup-offsite`, 03:30 UTC) copies the newest backups to an rclone destination, checks the copy, refuses to run without a fresh local backup, never overwrites an existing remote file, applies a retention window there, and a failure is mailed through the same alert hook as a failed backup. It is tested against a stand-in for rclone only (`tests/integration/backup-offsite.test.ts`). **Still open:** the destination is not chosen or configured, rclone is not installed on the server, nothing has run there, a restore from the off-server copy has not been rehearsed, and the staleness of the off-server copy is not part of the health check yet.
4. **Monitoring and alert delivery:** a vendor, the thresholds in `12-OPERATIONS.md` wired to a pager, error tracking, and a named on-call person. *Progress (2026-11-02):* a five-minute health check on the VPS now sends email alerts (after two failed runs, reminders every 6 hours, a recovery mail, and an immediate mail when the backup unit fails; `12-OPERATIONS.md`). **Still open:** one recipient is set and a test mail was accepted by Gmail, but inbox placement is unconfirmed and there is no second person; a failure of the whole server or its mail server is not reported (needs an outside monitor), and there is no error tracking, paging or named on-call person.
5. **Load test on a production-like deployment** (built app, real database service, realistic data volume), including authenticated flows. The first run on the VPS (built app, real database, anonymous GETs from the same host, before the public domain, so no Cloudflare, proxy or TLS) had no failures and a worst p95 of 113 ms; authenticated flows and realistic data are still untested. *Progress (2026-11-03):* `pnpm test:load:http` can now sign in (`LOAD_EMAILS`, `LOAD_PASSWORD`) and load signed-in pages; against the built app with a real database on a laptop, 200 requests at concurrency 10 per page on `/en/workspaces`, `/en/w/<slug>` and `/en/w/<slug>/tasks` with two accounts had no failures and a worst p95 of 165 ms (a smoke run, with almost no data). **Still open:** a run on the VPS through Cloudflare with realistic data volume, and write paths are not exercised.
6. **MFA** (at least for operators and workspace owners). *Done in code (2026-11-03, ADR-025):* two-step sign-in with an authenticator app and recovery codes (Better Auth two-factor plugin, account-level lockout built in); **operators cannot open `/admin` or use its actions without it**; owners are required to have it when `MFA_REQUIRED_FOR_OWNERS=true` (off by default so nobody is locked out before setting it up). Tested at the API level (code needed after the password, wrong code gives no session, recovery code works once, secret and codes are encrypted at rest) and in the browser (operator without it is redirected, turns it on, then reaches the console; a wrong code does not sign in). **Still open:** no QR code (the setup key is shown for manual entry), no passkeys, the owner rule is not exercised end to end because it is off in tests, password-reset does not require the second step, and the operator on the pilot server must turn it on before the next `/admin` visit. Shared rate-limit storage is done (ADR-019).
7. **AI provider and data residency (OD-08)** decided and recorded before `AI_BASE_URL` is set anywhere real.
8. **Legal and privacy** *(progress 2026-11-02, see below)*: privacy policy, terms, data processing terms, sub-processor list (hosting, email, Cloudflare Turnstile, AI provider, Google when calendar connection is on; the same pages also serve as the home page, privacy policy and terms that Google's OAuth consent screen requires before the app can leave Testing), a data-retention and deletion process for whole workspaces, and the breach-notification contact named in `12-OPERATIONS.md`. *Progress (2026-11-02):* public `/privacy` and `/terms` exist in English, Indonesian and Japanese (operator name and contact come from `LEGAL_OPERATOR_NAME` and `LEGAL_CONTACT_EMAIL`, required in production; Indonesian law, UU PDP No. 27/2022, named as the reference), they list the sub-processors that are in use today (Cloudflare incl. Turnstile, the hosting provider, Google only for calendar, own mail server; AI is stated as off), every page links to them in the footer, and sign-up points to them. Owners can request deletion of a workspace (Settings): 14-day waiting period, cancel any time, audited, shown to members and operators. **Still open:** the wording is a draft written by the implementing engineer and has **not been reviewed by a lawyer**; no separate data-processing agreement for customers exists (the terms and notice only); the breach-notification contact is the same single mailbox; there is no data export; the **removal of a workspace's data after the waiting period is built (2026-11-03, ADR-024)**: operator button in `/admin`, `pnpm purge:workspace`, and a worker sweep that is off unless `AUTO_PURGE_ENABLED=true`; tested against the real database with cross-tenant checks, but **not yet tried on the pilot server** with real files, and user accounts are not removed (a separate request); the hosting provider and its country are not named on the page and OD-01 is open; the 30-day answer time and the 14-day retention of logs and backups quoted in the notice are promises that operations must keep.
9. **Pricing and billing (OD-05).** Plans, limits and the operator console exist, but there are no prices, no checkout and no invoices. Charging customers needs a payment provider, tax handling and webhook handling with idempotency (ADR-015). A pilot can run without this.
10. **File uploads:** malware scanning before enabling uploads on public forms; the same question applies to member uploads for a public launch. *Progress (2026-11-03, ADR-025):* member uploads can be scanned by a ClamAV daemon (`MALWARE_SCAN=off|optional|required`, `CLAMD_HOST`, `CLAMD_PORT`); an infected file is always refused and audited (signature and size only), and with `required` a file that could not be scanned is refused too. Tested against a stand-in clamd that speaks the INSTREAM protocol. **Still open:** ClamAV is not installed on the server and the scan is off by default, signature updates (`freshclam`) are the operator's job, the scan is not tried against a real clamd, and **public forms still have no file field** (that feature is not built), so this unlocks uploads there but does not add them.

## Not blockers, but known
Semantic retrieval, PDF/office extraction, two-way calendar sync and Outlook (not planned, ADR-017), confirmation emails, an automation/workflow engine, a Redis adapter for several gateway instances, in-app feedback, and a visual design review.
