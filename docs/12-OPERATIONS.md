# 12 — Operations, Monitoring and Incident Procedures

How the platform is run once real tenants use it. Everything here is written for the people who operate the service, not for workspace members. Where a step needs infrastructure that is not chosen yet (OD-01 hosting, a monitoring vendor, a production email provider) the document says so instead of assuming it.

## Roles
- **Operator:** a person whose verified email is in `PLATFORM_ADMIN_EMAILS`. They can open `/admin`. Keep the list to the people who are on call. An operator is not a member of any workspace by virtue of being an operator.
- **Workspace owner/admin:** sees their own plan and usage at `/w/<slug>/billing`; cannot change the plan.

## The operator console (`/admin`)
- **Platform health (last 24 h):** workspaces, suspended workspaces, users and new users, queued jobs, how long the oldest due job has waited, failed jobs, stuck jobs (running with a lock older than 15 minutes), AI calls and AI errors. These are counts, never content.
- **Workspaces:** search by name or URL (100 rows at most), see plan, trial end, active members and AI tokens this month. Set a plan (optionally as a trial of 1–90 days) or switch the workspace off and on.
- Every change writes `billing.plan_changed`, `organization.suspended` or `organization.unsuspended` to that workspace's audit trail, with the operator as actor. Viewing the console is logged (operator id only).
- Setting a plan to **Unmetered** removes the subscription: the workspace has no plan limits (the state before billing existed).

## Plans (ADR-015)
Plans are set by hand. To move a customer: find the workspace, choose the plan, optionally a trial length, **Set plan**. The effect is immediate and needs no restart. Moving to a smaller plan never deletes data; see `07-SECURITY.md` for what stops working. A trial that ran out shows as "trial ended" and the workspace is on Free until the operator sets another plan.

## Signals to watch
There is no monitoring vendor yet. Until one is chosen, these are the signals, where to read them and when to act. All logs are structured JSON (pino) with a correlation id per request.

| Signal | Where | Act when |
| --- | --- | --- |
| App up and database reachable | `GET /api/health` (200 `ok`, 503 `degraded`) | two failed checks in a row, one minute apart |
| Job backlog | console: queued jobs and oldest due job | oldest due job waits more than 5 minutes |
| Worker dead | console: stuck jobs | any stuck job, or backlog growing with no jobs finishing |
| Failed jobs | console: failed jobs (24 h) | more than a handful, or any for one workspace repeatedly |
| AI provider trouble | console: AI errors against AI calls | errors above about 20 % of calls |
| Error rate | application logs, level `error` | a new error message repeating |
| Disk (file storage, database) | host | above 80 % |
| Realtime gateway | `GET /health` on the gateway port | not `ok` |

Alert delivery (paging) is **not set up**. Choosing a vendor and wiring these thresholds is a launch task (see `13-PRODUCTION-READINESS.md`).

## Incident procedure
1. **Declare.** Whoever notices opens an incident note (time, symptom, who is looking). One person is incident lead; others do not make changes without telling the lead.
2. **Classify.**
   - **SEV1:** possible exposure of one tenant's data to another, a leaked secret, or the service down for everyone.
   - **SEV2:** one feature or one tenant is down or badly degraded; data is safe.
   - **SEV3:** a bug with a workaround.
3. **Contain first, then diagnose.**
   - Suspected cross-tenant exposure or abusive tenant: **suspend the workspace(s)** in `/admin` (reversible, deletes nothing, stops access, public links, the calendar feed, realtime and downloads).
   - Leaked secret: rotate it (`BETTER_AUTH_SECRET` invalidates sessions; `REALTIME_PUBLISH_SECRET` must change on app and gateway together; the AI and Turnstile keys at their providers; `GOOGLE_CLIENT_SECRET` in the Google Cloud console (Clients, add a secret, then remove the old one); `CALENDAR_TOKEN_KEY` makes every stored calendar token unreadable, so people reconnect), then redeploy.
   - Bot abuse on public forms: enable Turnstile (`TURNSTILE_SITE_KEY`/`TURNSTILE_SECRET_KEY`), or unpublish the page.
4. **Diagnose** with the correlation id from the user's report or the failing log line. The audit trail (`audit_logs`) answers "who changed what, when" per workspace.
5. **Recover** with the runbook below, then confirm: health check green, backlog draining, a test sign-in works.
6. **Tell people.** SEV1: affected workspace owners are told what happened and what data was involved, and the legal/privacy contact decides on regulator notification (the clock for personal-data breaches is short; decide who that contact is before launch). SEV2: a short status note.
7. **Review within five working days:** timeline, cause, what detected it, what would have detected it sooner, follow-up tickets with owners. No blame; fix the system.

## Runbooks
**Health check returns 503.** The database is unreachable. Check the database host and its connection limit, then the app's `DATABASE_URL`. The app recovers on its own once the database is back; there is no state in the app process that needs repair.

**Jobs are stuck or the backlog grows.** Restart the worker (`pnpm worker`). The same process also sweeps for tasks due within a day every five minutes (ADR-020); if people say they get no deadline reminders, check that the worker is running. A job that was running when the worker died goes back to the queue once its lock is older than 5 minutes, as soon as a worker runs again (its attempt still counts). If one job type fails repeatedly, read `jobs.lastError` for that workspace (the error text, never the content); failed jobs stay in the table for inspection. Document indexing failures only affect search for that file.

**AI answers fail.** Check the console's AI errors, then the provider status. The planner and the assistant fail closed (an error message, no partial change). Setting a workspace's daily budget to 0 switches AI off for that workspace only.

**A workspace owner says they are locked out of a plan limit.** Open the console, read plan and usage, and either explain the limit or set a different plan. Remember a pending invitation holds a seat.

**A workspace must be taken offline** (abuse, legal request): suspend it. To bring it back, restore it. Neither deletes data.

**A workspace owner asks to delete the workspace** (owner: Settings, then Request deletion; the page is in the owner's menu under "Show all features"). The request is only recorded: the workspace keeps working, the owner can cancel, every member sees a notice, and `/admin` shows "Deletion requested ... can be removed after <date>" on the workspace (14 days after the request, `DELETION_GRACE_DAYS`). The request and any cancellation are in the audit trail (`organization.deletion_requested`, `organization.deletion_cancelled`). Before removing anything: check that the date has passed, that the request still stands (the owner may have cancelled), and that the person asking is the owner; take a fresh backup. **The removal itself is not automated and not yet designed in code**: it is not just `DELETE FROM organizations`, because `point_events`, `consent_events` and `contact_stage_changes` reject deletes by trigger, `audit_logs` and several foreign keys are `RESTRICT`, and uploaded files live on disk outside the database. Until a tested purge script exists (a launch item in `13-PRODUCTION-READINESS.md`), do not improvise this on the live database: plan it as a reviewed one-off, record what was removed, and tell the owner when it is done. The privacy notice promises removal from the live system after the waiting period and from backups within 14 days more; keep to that.

**A person asks for their personal data** (access, correction, deletion, withdrawal of consent; the privacy notice promises an answer within 30 days to the address in `LEGAL_CONTACT_EMAIL`). Confirm who they are, then: for account data (name, email, sessions), handle it directly; for data inside a customer's workspace (CRM contacts, form submissions, messages), pass the request to that workspace's owner, who can use the CRM erase function (`crm:erase`). Record the request and the answer.

**Realtime is down.** The product still works; pages need a refresh to show new messages. Restart `pnpm gateway`; clients reconnect and re-authorize every join.

## Backup and restore
- **What must be backed up together:** the PostgreSQL database **and** the file storage directory (`STORAGE_DIR`, or the object store once OD-04 is decided). A database restored without the files has file rows with no bytes; the reverse leaves orphan bytes.
- **Rehearsal (`pnpm rehearse:restore`):** builds a three-tenant data set with real stored files, takes a cold copy of the database directory and the file directory, destroys the originals, restarts from the copy, and fails unless every table's row count, the migration history, every file's content hash and the per-tenant task/file counts are identical. Latest local run: PASS (38 tables, 99 rows, 18 migrations, 9 files, 3 tenants, restart and verification in under a second; the data set is tiny, so the time says nothing about production).
- **What the rehearsal does not cover:** hot backups taken while the system is running (`pg_dump` or continuous archiving), point-in-time recovery, restoring into the real hosting, and the file store being a different system. Those need the production environment. Before launch someone must (a) choose the backup mechanism with the host (OD-01), (b) set retention, (c) run a restore into a clean environment from an actual backup, run `pnpm db:deploy` and the verification above against it, and (d) write down the measured recovery time and the maximum data loss the backup interval implies. Until then, no recovery-time or recovery-point promise should be made to customers.
- **Order when restoring:** database first, then files, then start the app; run `pnpm db:deploy` (it is a no-op when migrations are current), then spot-check one tenant.

## The VPS deployment (set up 2026-10-31, public since 2026-11-02)
The first real deployment runs on the owner's Plesk VPS (AlmaLinux 9, shared with other sites; Postgres 18 on the same host) and is reachable at `https://workspace.fts-tech.co.id` (ADR-022). The app, worker and gateway listen on `127.0.0.1` only; Plesk's nginx is the only public entrance.
- **Public access:** the subdomain is a Plesk subdomain behind Cloudflare (proxied DNS record). Cloudflare to the server uses a Cloudflare Origin certificate installed in Plesk, so the Cloudflare SSL/TLS mode must be **Full (strict)**; the certificate is not trusted by browsers that reach the server directly. In Plesk, "Proxy mode" is turned off for the subdomain and `deploy/plesk-nginx-vhost.conf` is installed as its additional nginx directives: `/` goes to port 3000, `/socket.io/` to port 4000 with the WebSocket upgrade headers, and the client address is taken from `CF-Connecting-IP` only when the request comes from Cloudflare's published ranges (refresh the list in the file now and then). With proxy mode on, nginx refuses the file with `duplicate location "/"`; Plesk keeps the previous configuration when that happens.
- **Public URLs in `.env`:** `BETTER_AUTH_URL`, `APP_URL` and `REALTIME_PUBLIC_URL` are all `https://workspace.fts-tech.co.id` (browser and gateway must share one host name for the session cookie). `REALTIME_URL` stays `http://127.0.0.1:4000` (server to gateway). Restart `fts-web` and `fts-gateway` after changing them. If Google Calendar is switched on, the redirect URI in Google Cloud becomes `https://workspace.fts-tech.co.id/api/integrations/google/callback`.
- **Layout:** user `fts` (no login), code in `/opt/fts-workspace/app` (copied from the Plesk repository by the deploy script, no `.git`), secrets in `/opt/fts-workspace/.env` (mode 600), files in `/opt/fts-workspace/files`, backups in `/opt/fts-workspace/backups`, scripts in `/opt/fts-workspace/bin`. Node and pnpm are the ones Plesk ships (`/opt/plesk/node/24`); if Plesk changes that path, the units must follow.
- **Services (systemd, restart on failure, start at boot):** `fts-web` (`next start`, port 3000), `fts-worker`, `fts-gateway` (port 4000). Logs: `journalctl -u fts-web` and so on.
- **Database:** `fts_workspace`, owned by the role `fts_app`, which can reach only that database.
- **Update (Plesk Git, manual):** push to GitHub `main`, then in Plesk open Git for the subdomain, **Pull now**, then **Deploy now**. The repository `fts-workspace.git` is deployed to `/workspace-src` (outside the web root) and its post-deployment action runs `sudo /usr/local/sbin/fts-deploy.sh` (source: `deploy/fts-deploy.sh`). The script takes a lock, runs a backup, copies the pulled commit into `/opt/fts-workspace/app` (keeping `.env`, `node_modules`, `.next` and `src/generated`), runs `pnpm install --frozen-lockfile`, `prisma migrate deploy` and `next build` as `fts` with the same `.env` the services use, restarts the three services, waits for `/api/health` and writes the commit and time to `/opt/fts-workspace/DEPLOYED`. It exits non-zero when the health check fails (`journalctl -u fts-web -n 50`). It can also be run by hand as root over SSH. Keep the mode **Manual**: Automatic would deploy every push without waiting for CI. The build runs while the old version is still serving, so a request can fail during the few seconds of the restart. There is no automatic rollback: to go back, push a revert (or an older commit) and deploy again; migrations are additive (see below).
- **Why a root script:** the app belongs to `fts`, but Plesk runs post-deployment actions as the subscription's system user, which cannot write `/opt/fts-workspace` or restart units. `/etc/sudoers.d/fts-deploy` (template: `deploy/fts-deploy.sudoers`) lets that one user run exactly that script as root, without arguments. The script lives in `/usr/local/sbin`, owned by root, never in a folder the app user can write: otherwise a compromised app could change what runs as root. Anyone who can log in to Plesk as that subscription can therefore start a deploy of whatever `main` holds.
- **Email:** `EMAIL_TRANSPORT=smtp` with `SMTP_URL` pointing at the Plesk mail server on the same VPS, mailbox `no-reply@fts-tech.co.id` (SPF lists the VPS, DKIM and DMARC records exist, DMARC is still `p=none`). The login was checked with the app's own credentials and a real sign-up verification email arrived on 2026-11-02. See `13-PRODUCTION-READINESS.md` for what is still untested.
- **Realtime:** checked in a browser on 2026-11-02: a chat message typed in one session appeared in another without a refresh (WebSocket through Cloudflare and nginx to the gateway). An anonymous request to `/socket.io/` answers 403 by design (the handshake needs the session cookie), so that is not a failure signal.
- **Backups:** `fts-backup.timer` runs `bin/backup.sh` daily at about 02:30 UTC: a custom-format `pg_dump`, a tarball of the files, a SHA-256 list, a check that the dump can be listed, and deletion of copies older than 14 days. **They stay on the same server**: a copy off the server is still open, and without it a lost server loses the backups too.
- **Restore rehearsal (2026-10-31):** the dump from the real backup was restored into a scratch database in 0.5 s; all 44 tables had the same row counts as the source and the scratch database was dropped. The database was nearly empty (no tenants yet), so this proves the mechanism, not recovery time with real data. The files archive was not restored in this run. Repeat it with data before launch. Restore command: `pg_restore --no-owner --role=fts_app --dbname=<empty db> --exit-on-error < db-<stamp>.dump` as the `postgres` user (stdin keeps the backup folder private).
- **Health check:** `fts-health.timer` runs every 5 minutes and fails the unit, with a JSON line in the journal, when `/api/health`, the gateway, the worker, disk space (90%) or backup freshness (26 hours) is wrong. **Email alerts (2026-11-02):** the timer runs `bin/healthcheck-notify.sh` (source: `deploy/healthcheck-notify.sh`, drop-in `deploy/systemd/fts-health.service.d-notify.conf`), which runs the check and mails the address in `/opt/fts-workspace/alert.conf` (`ALERT_TO="..."`, owned by `fts`, mode 600; empty means nothing is sent and the journal says so) through the same SMTP account as the app. A problem is mailed after two failed runs in a row (so a deploy restart does not page anyone), repeated every 6 hours while it lasts, and followed by an "OK again" mail. A failed `fts-backup.service` is mailed at once through `OnFailure=` (`deploy/systemd/`). The flow was tested with a simulated failure delivered to the local `no-reply` mailbox, and a test mail (`healthcheck-notify.sh --test`) was accepted by Gmail on 2026-11-02 for the recipient now set in `alert.conf`; whether it lands in the inbox or in spam was left to the recipient to confirm. It cannot report that the whole server or its mail server is down: add an outside monitor on `https://workspace.fts-tech.co.id/api/health` for that. Also check with `systemctl list-units --failed`.
- **Captcha (2026-11-02):** Turnstile is on for public forms and booking pages: `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` are set in `/opt/fts-workspace/.env` (the widget in the Cloudflare dashboard lists only `workspace.fts-tech.co.id`, mode Managed). Both keys are read at runtime, so changing them needs only `systemctl restart fts-web`. To rotate the secret, use "Rotate secret" on the widget and replace the value in `.env`. Checked: Cloudflare's siteverify accepts the secret from the server (a fake token gets `invalid-input-response`, not `invalid-input-secret`). Not checked in a browser: the workspace has no published form or booking page yet, so the widget on a live page and a real submission are still to be tried when the first one exists.
- **HTTP load test (2026-10-31):** the built app on this host with the real database, anonymous GETs from the same machine at concurrency 20 and 400 requests per path: no failures; p95 37 ms (`/api/health`) and 84–113 ms (the sign-in pages, three languages). It does not include Cloudflare, the Plesk proxy or TLS, authenticated flows or realistic data volume.

## Deploying and rolling back
- Apply migrations with `pnpm db:deploy` before starting the new version. Each migration notes its manual rollback SQL; most are additive, so rolling the application back to the previous version with the new schema in place is safe.
- Rolling back the billing migration (`20261030130000_billing`) means dropping `subscriptions` and `organizations.suspendedAt`; do it only after rolling the application back first.
- The app refuses to start in production with `EMAIL_TRANSPORT=log`. Set `EMAIL_TRANSPORT=smtp`, `SMTP_URL` (for example `smtps://user:password@smtp.example.com:465`) and `EMAIL_FROM`. The SMTP URL carries a password: keep it in the secret store, never in the repository, and rotate it at the provider if it leaks (restart the app after changing it). What is configured on the VPS and what is still untested is described under "Email" in the VPS section and in `13-PRODUCTION-READINESS.md`.
- Migration `20261030160000_auth_rate_limits` adds the `rate_limits` table (rollback: `DROP TABLE "rate_limits"`).

## Environment variables added in Phase 5
`BILLING_ENABLED` (default `false`), `BILLING_TRIAL_DAYS` (default 14, 1–90), `PLATFORM_ADMIN_EMAILS` (comma-separated; empty means nobody can open `/admin`).

`LEGAL_OPERATOR_NAME` and `LEGAL_CONTACT_EMAIL` (added 2026-11-02): the name and the privacy contact printed on `/privacy` and `/terms`. **Both are required in production** (the app refuses to start without them, like the email transport check), so those pages never go live without a name and a contact. On the pilot server they are set in `/opt/fts-workspace/.env` before the deploy that ships the pages.
